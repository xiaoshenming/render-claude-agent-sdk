# 输入、输出与审计日志

## 1. Agent 实际看到什么

模型只看到：

1. `class Solution(BaseConfigScene)`；
2. 两个 Reviewer 的结构化结论；
3. 七个受控工具的紧凑返回；
4. 当前 revision 和 Hash；
5. 最多 20 个阻塞布局 issue。

模型看不到文件头、框架 helper、合同函数、整个仓库、Manim 日志、完整 BBox
帧数组、密钥、素材目录或任意 Bash。

## 2. 七个工具

| 工具 | 用途 |
| --- | --- |
| `read_solution` | 读取当前 Solution 和代码 Hash |
| `check_relation` | 检查确定性数值/几何关系 |
| `record_findings` | 冻结 Reviewer 问题 |
| `apply_patch` | 绑定 revision/Hash 的精确块级替换 |
| `validate_revision` | 真实渲染并将结果反馈给 Agent |
| `inspect_layout` | 导出 BBox 并返回紧凑阻塞问题 |
| `submit_revision` | 提交候选给独立外层门禁 |

没有 Bash、Read、Edit、Write、Glob、Grep、Web 或任意路径权限。文件读写由
Harness 执行，R0 永远不变。

## 3. 每题输出（跑完：PROPOSED / HOLD）

```text
run/
├── input/
│   ├── problem.snapshot
│   └── candidate.R0.py
├── revisions/
│   ├── R0.baseline.py
│   ├── R1.logic.py            # 命名规则 R<n>.<scope>.py
│   └── R2.layout.py           # n 随动态 Patch 预算最多到 R7
├── evidence/
│   ├── findings.json
│   ├── revisions.json
│   ├── layout.R0.baseline.json
│   ├── validation.<revision>.json
│   └── layout.<revision>.json
├── logs/
│   ├── agent_call.json
│   ├── parent-sdk-messages.jsonl
│   ├── subagent-results.json
│   ├── tool_calls.jsonl
│   └── run_summary.json
├── agent_runtime/
├── acceptance_runtime/
└── output/
    ├── decision.json
    ├── proposed_candidate.py
    └── rollback.R0.py
```

`layout.R0.baseline.json` 是会话开始前对 R0 做的独立布局复检。它同时决定本题的
Patch 预算：`blocking_count <= 2` 给 5 个 Patch，`3..8` 给 6 个，`> 8` 给 7 个。

## 3.1 失败归档（FAILED）

Agent、工具、运行时或预算异常导致中断时，不写 `proposed_candidate.py`，改写失败
归档：

```text
run/
├── evidence/
│   └── layout.R0.baseline.json
├── logs/
│   ├── agent_call.partial.json
│   ├── parent-sdk-messages.jsonl   # 中断时同样有真实内容
│   ├── subagent-results.json       # 中断时同样有真实内容
│   ├── tool_calls.jsonl
│   └── failure.json
└── output/
    ├── decision.json               # {"decision": "FAILED", ...}
    ├── last_candidate.<Rn>.py
    └── best_render_passed.<Rn>.py  # 可能不存在
```

`failure.json` 字段：

| 字段 | 含义 |
| --- | --- |
| `status` | `FAILED_TIMEOUT` / `FAILED_TOKEN_BUDGET` / `FAILED_PATCH_BUDGET` / `FAILED_LAYOUT_INSPECT_BUDGET` / `FAILED_RENDER` / `FAILED_REVIEWER_SCHEMA` / `FAILED_NO_PATCH` / `FAILED_EXTERNAL_ACCEPTANCE` |
| `error_type` / `error` | 异常类型与原文 |
| `last_revision_id` / `last_revision_code_hash` | 中断时的当前 revision |
| `best_render_passed` | `{revision_id, blocking_count, layout_inspected}`，无则为 `null` |
| `tokens` / `usage_complete` | Token 用量，以及 SDK 用量是否完整对账 |
| `external_tool_ms` | 被排除在 Agent 推理时限之外的外部工具墙钟 |
| `turns` / `tool_calls` | 中断时已用轮次与工具调用数 |

`last_candidate.<Rn>.py` 是中断瞬间的当前 revision，未经任何验收。

`best_render_passed.<Rn>.py` 是过程中渲染通过的最好候选，**它是证据不是交付
物**：可能仍带 blocking 布局问题，也可能压根没做过布局复检（对应
`layout_inspected: false`，`blocking_count: null`）。不要直接拿它当成品发出去；
要用先按第 4 节的标准重新独立验收。

## 4. 如何确认真的跑完

不能只看进程退出码。`PROPOSED` 至少同时满足：

1. `output/proposed_candidate.py` 存在；
2. `output/decision.json` 的 revision、code Hash、problem Hash 一致；
3. `acceptance_runtime/<revision>/ffprobe.json` 显示正时长视频；
4. 独立布局结果 `verified=true`；
5. 独立布局结果 `blocking_count=0`；
6. Agent 实际调用了 `submit_revision`；
7. 外层使用了不同于 Agent 内部的 Validator/Inspector 实例。

## 5. 常用日志

- 看 Reviewer 判断：`logs/subagent-results.json`
- 看 Agent 每一步：`logs/tool_calls.jsonl`
- 看 Tokens/耗时/轮次：`logs/run_summary.json`
- 看最终原因：`output/decision.json`
- 看中断原因：`logs/failure.json`
- 看代码改了什么：对比 `revisions/R0.baseline.py` 与最终 revision
- 看渲染失败：`agent_runtime/**/render.log`
- 看最终视频事实：`acceptance_runtime/**/ffprobe.json`
- 看重叠事实：`acceptance_runtime/**/layout_detector.json`

## 6. 已知验证边界

当前外层门禁可独立证明：

- 候选真实可渲染；
- 视频流存在且正时长；
- BBox 检测已执行；
- 没有 detector 定义的阻塞重叠；
- 修改遵守 revision、Hash、题目和语义保护。

当前外层门禁不能独立证明所有数学推理正确。数学逻辑由双 Reviewer 审查，
修复后尚无第三个独立 Final Logic Verifier。故 `PROPOSED` 应理解为统一 Agent
的预验收候选，正式交付仍应进入平台 FinalConsistencyGate/评分链。
