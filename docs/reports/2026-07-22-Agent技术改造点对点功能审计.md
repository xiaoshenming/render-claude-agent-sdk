## 4. 反馈主线与原子功能点

### A. 逻辑工具合同

#### A-01 🟠 DuplicateRead 从硬失败改为缓存返回

- **代码**：[guards.py](../../src/manim_quality/agents/guards.py#L125)、[test_guards.py](../../tests/unit/agents/test_guards.py#L80)
- **测试 / 入口**：现有测试明确断言重复 Read 抛出 `DuplicateRead`；这正是需要反转的旧合同。
- **状态描述**：重复读取签名已经可识别，但当前处理方式是抛异常并终止 Agent。
- **缺口**：缺少首读结果缓存、重复读计数和非阻断告警；33 条逻辑重放的 4 条 rejected 中有 3 条命中该问题。
- **下一步**：
  1. 新建 Read 结果缓存，以路径、版本、offset、limit 为键；
  2. 将重复 Read 改为返回缓存内容并记录 `duplicate_read_count`；
  3. 改写测试，断言第二次读取不抛异常且不重复访问磁盘；
  4. 重放三个已知 Job，确认不再因 DuplicateRead rejected。

#### A-02 🟠 Verifier 证据允许绑定实际 diff 新行

- **代码**：[_verifier_evidence.py](../../src/manim_quality/logic/_verifier_evidence.py#L12)、[test_verifier_batch2.py](../../tests/unit/logic/test_verifier_batch2.py#L167)
- **测试 / 入口**：`bind_candidate_evidence()` 已校验 Scene、行号、excerpt 和 changed hunk，但第 39—42 行要求修复证据必须机械关联原 issue hunk。
- **状态描述**：Verifier 证据结构完整，但合理的新行引用仍可能被旧行绑定拒绝。
- **缺口**：缺少“实际 diff 新行/邻近替代行/结构化新值”三种可接受证据；绑定失败仍会丢候选。
- **下一步**：
  1. 抽出 `CandidateEvidenceMatch`，区分 exact、diff-neighbor、semantic-value、unbound；
  2. exact/diff-neighbor 允许自动通过，semantic-value 标记人工风险；
  3. unbound 不得删除已编译候选，只转 `human_review`；
  4. 用 `01KXTBARWSRQ24KKGXJ1B5WPR1` 回归候选保留。

## 6. 证据包设计与交付内容

### 6.1 交付位置

```text

```

压缩包与 SHA256 在最终收尾阶段生成，README 中记录仓库 commit 和 server3 部署标记。

### 6.2 精选标准

保留：

- 批次 `summary.json`、`inventory.json`、`progress.jsonl`；
- Reviewer `review_report`、review attempts；
- Coder/Verifier calls、repair result、before/after 和 diff；
- 布局 issue classification、每轮 SDK messages、check result、layout case log；
- 运行态、数据库去重汇总和关键 Job 索引；
- README、文件清单、SHA256。

排除：

- MP4、PNG、Tex、SVG 和 Manim 媒体缓存；
- 重复且数 MB 的 probe stdout；
- `.env`、API Key、Bearer、完整供应商 URL；
- 与 Agent 根因无关的全量 journal。

### 6.3 推荐阅读顺序

1. 先读根目录 `README.md`；
2. 再看逻辑 33 条和重叠新 50 条的 `summary.json`；
3. 按 README 的典型 Job 进入逐 case 目录；
4. 最后对照本审计文档中的代码入口建工单。
